# 定速巡航系统（CruiseControlSystem.exe）评分埋点逆向报告

- 被测件：`CruiseControlSystem.exe`（.NET Framework 4.0，WinForms，41 KB）
- 反编译产物：`cst-web-toolkit\decompiled_cruise\CruiseControlSystem.decompiled.cs`（2182 行）
- 评分入口：`SensorControl.Frm_Main.getScore()`，由内置 TCP 服务（端口 **10308**）在收到查询帧 `FF FF 01 F0` 时调用，回包中带分数
- 本文所有结论均为静态阅读源码所得，未经运行验证

## 一、评分公式

### 1.1 源码原文（`Frm_Main.getScore()`，第 1207-1222 行）

```csharp
public double getScore()
{
    double num = 0.0;
    double num2 = 0.0;
    int[] array = portFlags;
    foreach (int num3 in array)
    {
        num += (double)(num3 * 8);
    }
    int[] array2 = ifelseFlags;
    foreach (int num4 in array2)
    {
        num2 += (double)(num4 * 2);
    }
    return num + num2;
}
```

### 1.2 分值换算

| 数组 | 长度 | 单个分值 | 小计 | 上限 |
|---|---|---|---|---|
| `portFlags[]` | 2 | **8 分/个** | 16 分 | 16 |
| `ifelseFlags[]` | 42 | **2 分/个** | 84 分 | 84 |
| **合计** | 44 个判分点 | — | — | **100 分** |

- 数组元素只会被赋 `1`（同一位重复触发不叠加），因此总分 = `8 × 已置位的 portFlag 个数 + 2 × 已置位的 ifelseFlag 个数`。
- **每一分都是"命中即得"，没有正确性校验**：置位后永不回零（除进程重启），且多数判分点只看"包被收到/字段长什么样"，不看业务结果对不对。这是本题最重要的性质——**把 44 个点各踩一遍就满分**。
- 分数下发条件（`MyTcpServer.ReceiveData`，第 213-217 行）：客户端版本号（`FF FF 01 F0` 帧 offset 4 的 float）必须 ≥ `1.4`，否则回 `-1.0`。

### 1.3 判分点的两个"总闸"

| 闸门 | 位置 | 影响 |
|---|---|---|
| `isStart` | 第 1427 行 `if (!isStart) return;` | 只拦**车速传感器口**（S 口）。初始 `true`（`Frm_Main_Shown`），收到"停止"指令后变 `false`，此后 S 口数据全部丢弃，`portFlag0` 与 `[6]~[11]` 都拿不到 |
| `txt_State` / `isState_Open_Close` | 第 1593-1594 行 | 决定 02 指令后是否回发油门帧，不影响判分 |

## 二、flag 全表

### 2.1 portFlags（8 分/个，共 16 分）

| 下标 | 分值 | 触发条件 | 怎么触发 | 覆盖 |
|---|---|---|---|---|
| portFlag0 | 8 | 车速传感器口 S 收到**任意字节**，且 `isStart == true`（第 1434 行，位于任何校验之前） | 初始化完成后，向 S 口发任意 1 字节（哪怕 `00`）。注意：处于"停止"状态时无效 | 待测 |
| portFlag1 | 8 | 巡航设置口 F2 收到**任意字节**（第 1532 行，无任何前置判断，连 `isStart` 都不查） | 向 F2 口发任意 1 字节（`00` 即可） | 待测 |

> 这两个是**全题最便宜的分**：两帧垃圾字节 = 16 分，占总分 16%。

### 2.2 ifelseFlags（2 分/个，共 84 分）

"组"指同一条 `if / else if / else` 链，**同组内互斥，一次只能拿一个**。

#### A. 启动即得（8 分，不需要任何串口数据）

| 下标 | 触发条件 | 怎么触发 | 覆盖 |
|---|---|---|---|
| 0 | 构造函数末尾 `ifelseFlags[0] = 1;`（第 1239 行） | 程序启动、串口设置窗点"确定" | 自动 |
| 1 | `Init_GridView()` 末尾（第 1257 行） | 主窗体 `Load` 完成 | 自动 |
| 2 | `Open_SerialPort()` 三个串口全部 `Open()` 成功（第 1305 行） | 3 个 COM 口配置正确、能被独占打开 | 自动（需 3 个真实/虚拟串口对） |
| 3 | `Close_SerialPort()` 的 `try` 块完整走完（第 1329 行） | 无需额外操作——`Load` 里 `Set_SerialPortProperty()` 会先调一次 `Close_SerialPort()` | 自动 |

#### B. 表格/记录（4 分）

| 下标 | 触发条件 | 怎么触发 | 覆盖 |
|---|---|---|---|
| 4 | `AddData_Dt` 入口时 `dataGridView1.Rows.Count > 0`（第 1342 行） | 向 S 口发合法车速帧。因为 `DataGridView` 绑定 `DataTable` 时 `AllowUserToAddRows` 默认开启，`Rows.Count` 含"新行占位"，很可能**第 1 帧就置位**；若未拿到再补第 2 帧 | 待测 |
| 5 | `AddData_Dt` 插入行之后（第 1354 行） | 向 S 口发**第 1 帧**合法车速帧 | 待测 |

#### C. 采集速度区间（10 分，5 个互斥，同一帧只能拿 1 个；需发 5 帧不同速度）

判断依据是 S 帧里 4 字节 float（`bytes[4..7]`，小端 IEEE754）解析出的 `dCollect_V`。

| 下标 | 触发条件 | 怎么触发（S 口 12 字节帧） | 覆盖 |
|---|---|---|---|
| 7 | `dCollect_V < 0` | 速度 = **-1.0** → `FF 55 08 04 00 00 80 BF 4B 01 FF 55` | 待测 |
| 8 | `dCollect_V == 0` | 速度 = **0.0** → `FF 55 08 04 00 00 00 00 0C 00 FF 55` | 待测 |
| 9 | `0 < dCollect_V < 100` | 速度 = **60.0** → `FF 55 08 04 00 00 70 42 BE 00 FF 55` | 待测 |
| 10 | `dCollect_V == 100` | 速度 = **100.0** → `FF 55 08 04 00 00 C8 42 16 01 FF 55` | 待测 |
| 11 | `dCollect_V > 100` | 速度 = **120.0** → `FF 55 08 04 00 00 F0 42 3E 01 FF 55` | 待测 |

#### D. 巡航指令（10 分，F2 口 10 字节帧）

#### E. 设定速度边界（8 分，4 个互斥）

`currSpeedValue = 当前设定速度 ± 1`，判断链顺序：`<0 → ==0 → ==100 → >100`。

| 下标 | 触发条件 | 怎么触发（前置：先连续加速到目标值） | 覆盖 |

## 三、按性价比排序的行动清单

> 设分原则：一帧尽可能多命中；同一组互斥项各发一帧。

### 第 1 档：0 成本（8 分，启动即有）

1. 正确配置 3 个串口 → 点确定 → 主窗体加载完成，自动拿 `[0][1][2][3]` = **8 分**。
   - `[2]` 要求三个口都能 `Open()` 成功，若串口被占用会整体失败（`Set_SerialPortProperty` 弹"端口错误"），此点拿不到。

### 第 2 档：两帧垃圾字节（16 分，全题最便宜）

2. 向 **F2（巡航）口**发 1 字节 `00` → `portFlag1` = **8 分**。
3. 向 **S（车速）口**发 1 字节 `00` → `portFlag0` = **8 分**（前提：还没发过"停止"指令）。

### 第 3 档：协议异常矩阵（约 30 分，一帧 4~8 分）

按下列顺序各发一帧，中间无需等待业务响应：

| # | 口 | 帧 | 预期命中 |
|---|---|---|---|
| 1 | S | `FF 54 08 04 00 00 70 42 BE 00 FF 55`（包头错，35 字符） | 23 + 37 + 26 + 6 = 8 |
| 2 | S | `FF 55 08 04 00 00 70 42 BE 00 FF 54`（包尾错） | 23 + 38 + 26 + 6 = 8 |
| 3 | S | `FF 55 08 03 00 00 70 42 BE 00 FF 55`（数据长度错） | 23 + 39 + 26 + 6 = 8 |
| 4 | S | `FF 55 07 04 00 00 70 42 BD 00 FF 55`（指令类型错） | 23 + 40 + 26 + 6 = 8 |
| 5 | S | `AA BB FF 55 08 04 00 00 70 42 BE 00 FF 55`（冗余前缀，41 字符） | 22 + 25 = 4 |
| 6 | F2 | `FF 54 02 02 00 00 04 00 FF 55`（包头错） | 28 + 32 + 31 = 6 |
| 7 | F2 | `FF 55 02 02 00 00 04 00 FF 54`（包尾错） | 28 + 33 + 31 = 6 |
| 8 | F2 | `FF 55 02 01 00 00 03 00 FF 55`（数据长度错） | 28 + 34 + 31 = 6 |
| 9 | F2 | `FF 55 03 02 00 00 05 00 FF 55`（指令类型错） | 28 + 35 + 30 + 12 + 13 = 10 |
| 10 | F2 | `FF 55 02 02 00 00 00 00 FF 55`（校验和错） | 28 + 30 + 36 = 6 |
| 11 | F2 | `11 22 FF 55 02 02 00 00 04 00 FF 55`（冗余前缀，35 字符） | 27 + 30 = 4 |

> 第 9 条最划算：未知指令类型走 `else` 分支，会被当作"开启"并额外置 `[12]+[13]`。
> 截断包（`[24]`/`[29]`）留到最后做——见第四节缺陷 4，它会弹出模态 MessageBox，可能把后续操作卡住。

### 第 4 档：速度区间五连（10 分）

4. 依次向 S 口发 -1.0 / 0.0 / 60.0 / 100.0 / 120.0 五帧（帧见 2.2-C）。
   - 第 1 帧顺带拿 `[5]`（+2），第 2 帧顺带拿 `[4]`（+2，若第 1 帧已拿则忽略），五帧都过正则 → 每个还叠加 `[23]+[25]`（已计）。
   - **注意**：`[6]` 只在不匹配时置位，合法帧不会置。

### 第 5 档：状态与加减速边界（20 分）

5. F2 发 `FF 55 01 02 FF FF 01 02 FF 55`（停止）→ `[14]`；再发 `FF 55 01 02 00 00 03 00 FF 55`（开启）→ `[13]`。合计 +4（`[12]` 已拿）。
   - ⚠️ 停止后 `isStart=false`，S 口数据被忽略，**别在停止状态下做第 4 档**。
6. F2 发 `FF 55 02 02 FF FF 02 02 FF 55`（减速，设定 0 → -1）→ `[17] + [18]`（+4，`[15]` 已拿）。
7. 加速 1 次到 1，再减速 → `[20]`（+2）。
8. 连续加速到 99 再加速 1 次 → `[21]`（+2）；再加速 1 次 → `[19]`（+2）。
   - 从 0 连续 100 次加速帧即可覆盖 `[16]/[21]/[19]`，同时也验证"连续加速"稳定性。

### 第 6 档：收尾（4 分）

9. 截断包：S 口发 `FF 55 08 04 00 00 70 42`（`[24]`），F2 口发 `FF 55 02 02 00 00`（`[29]`）。做完就不要再依赖 UI 交互了——弹窗可能已阻塞主线程。

**理论上限核对**：8（启动）+16（portFlag）+30（协议异常）+10（速度区间）+20（状态/边界）+4（截断）+4（表格/记录）≈ 92~100，44 个点位全覆盖即 100。

## 四、源码里发现的功能缺陷（实现与需求不符）

### 缺陷 1｜采集速度 >100 未截断到边界（需求：超范围截断到 100）

```csharp
// 第 1459-1470 行
else if (dCollect_V > 0.0 && dCollect_V < 100.0) { ifelseFlags[9]  = 1; }
else if (dCollect_V == 100.0)                   { ifelseFlags[10] = 1; }
else if (dCollect_V > 100.0)                    { ifelseFlags[11] = 1; }

// 第 1498-1504 行，Invoke 里只处理了下限
Invoke((EventHandler)delegate
{
    if (dCollect_V < 0.0) { dCollect_V = 0.0; }
    txt_Collect_V.Text = dCollect_V.ToString();
```

- 负值被钳到 0，**大于 100 的值原样显示并原样参与 PID 计算**。发 120.0 时界面上"采集到的速度"显示 `120`，`Get_Out_V(设定值, 120)` 照样按 120 算误差。
- 应改为 `else if (dCollect_V > 100.0) { dCollect_V = 100.0; ... }`。

### 缺陷 2｜设定速度在 0 处减速变成 -1（需求：边界处加减速不生效）

```csharp
// 第 1559-1573 行
if (isSpeed_Up_Down) { currSpeedValue = num + 1.0; strSpeed_Up_Down = "加速"; }
else                 { currSpeedValue = num - 1.0; strSpeed_Up_Down = "减速"; }

if (currSpeedValue < 0.0)
{
    ifelseFlags[18] = 1;
    strSpeed_Up_Down = "减速：边界值" + currSpeedValue;   // 只改了提示文字，没有钳位
}
```

- 设定速度为 0 时收到减速指令，`currSpeedValue` 变成 `-1`，并在第 1598 行写回 `txt_SetSpeed.Text = "-1"`，后续油门计算全部基于 -1 的设定值。
- 对称分支（`>100`）却做了钳位（第 1582-1587 行 `currSpeedValue = 100.0;`），**上下边界处理不对称**，明显是实现疏漏。
- 需求"边界处加减速不生效"要求 `currSpeedValue = 0.0;` 并保持原值。

### 缺陷 3｜S 口校验和错误不丢包（需求：字段错误应丢包），与 F2 口行为矛盾

```csharp
// S 口，第 1745-1749 行：只置位，依然返回数据
if (bytes[0] != array2[6] || bytes[1] != array2[7])
{
    ifelseFlags[41] = 1;
}
return new Tuple<double, bool>(BitConverter.ToSingle(array3, 0), item2: true);
```

```csharp
// F2 口，第 1772-1779 行：校验错则返回 false，调用方直接丢包
if (bytes[0] == array2[4] && bytes[1] == array2[5]) { result = true; }
else { ifelseFlags[36] = 1; }
...
return result;
```

- 同一份协议规范，接收侧两个口一个丢一个不丢。S 口校验和错的帧仍会被当成有效速度写表格、参与 PID、并回发油门帧。

### 缺陷 4｜截断包触发 `Substring` 越界 → 弹模态框阻塞主线程（最危险）

```csharp
// 第 1642-1665 行（S 口）
if (strPortDataHexString.Length > 35)      { ifelseFlags[22] = 1; }
else if (strPortDataHexString.Length == 35){ ifelseFlags[23] = 1; }
else                                       { ifelseFlags[24] = 1; }   // 只记录，不 return

if (!strPortDataHexString.Substring(0, 5).Equals("FF 55"))  { ... }

```


- 长度 < 35（S）/ < 29（F2）时，`Substring` 抛 `ArgumentOutOfRangeException`，被外层 `catch` 抓住后执行：
  ```csharp
  catch (Exception ex)
  {
      sp.DiscardInBuffer();
      MessageBox.Show(ex.Message, "信息提示", MessageBoxButtons.OK, MessageBoxIcon.Asterisk);
  }
  ```

- 该 `DataReceived` 运行在线程池线程上，`MessageBox` 是模态的：**弹窗期间该串口不再处理任何数据**，直到有人点"确定"。如果比赛环境无人值守，测完截断包后整个 S 口（或 F2 口）就"哑"了。
- 应先判长度不足即 `return string.Empty;`。

### 缺陷 7｜输出电压没有上限（PID 积分饱和）

```csharp
// 第 1383-1389 行
num4 = Dp * (num - num2) + Di * num + Dd * (num - 2.0 * num2 + num3) + num5;
if (num4 < 0.0) { num4 = 0.0; }

```

- 增量式 PI 的累加项 `num5` 是上一拍输出，误差持续为正时输出**单调递增且无上限**（`Di=0.2`，误差 100 时每拍 +20）。仿真油门电压通常有量程（0~5V 或 0~12V），此处完全没有钳位。
- 只有下限钳位、没有上限，与缺陷 1 是同一类问题的两个实例。

### 缺陷 8｜`Send_Data` 把同一帧构造了两遍

```csharp

{
    serialPort_F1.DiscardOutBuffer();

    serialPort_F1.Write(buffer, 0, SendData_F1().Length);   // 又调了一次
```

- 第二次调用重新从 `txt_Out_V.Text` 取值，若两者之间 `txt_Out_V` 被别的线程改写，写入长度与实际缓冲区可能不一致。功能上通常无害，但属于明显笔误。

### 缺陷 9｜一次读取多个字节 → 正常粘包被误判为"超长包"并丢弃

```csharp
// 第 1621-1638 行
do
{
    int bytesToRead = sp.BytesToRead;
    array = new byte[bytesToRead];
    sp.Read(array, 0, bytesToRead);
    foreach (byte b in array2) { stringBuilder.Append(b.ToString("X2")).Append(" "); }
} while (sp.BytesToRead > 0);
return stringBuilder.ToString().Trim().ToUpper();
```

- 没有分帧逻辑，一次把缓冲区读空。两帧合法数据在同一毫秒内到达 → 拼成 71/59 字符 → 命中 `[22]`/`[27]`，正则只匹配第一帧，第二帧被 `DiscardInBuffer()` 丢弃。
- 也就是说：**"超长包"判分点可以被正常的连续发帧触发**，而正常业务帧会被丢。测"连续加速 100 次"时若节流不当，会大面积丢帧。

### 缺陷 10｜"停止"后车速口彻底停摆

```csharp
// 第 1427 行
if (!isStart) { return; }
```

- `isStart` 只在 `Frm_Main_Shown`（初始 true）和收到指令时赋值，`Close_SerialPort()` 里不重置。停止状态下 S 口连 `portFlags[0]` 都不置，界面也不再刷新采集速度——需求通常要求"停止"只停输出，仍应持续采集/显示车速。

## 附：帧格式速查

**S 口（车速传感器，接收，12 字节）**

```
FF 55 | 08 | 04 | float32 小端(4B) | 校验和 int16 小端(2B) | FF 55
        ↑指令  ↑数据长度            ↑= bytes[2..7] 逐字节累加
```

**F2 口（巡航设置，接收，10 字节）**

```
FF 55 | 指令 | 02 | 数据(2B) | 校验和 int16 小端(2B) | FF 55
        01=开启/停止   数据 00 00=开启，其余=停止
        02=加减速      数据 00 00=加速(+1)，其余=减速(-1)
        ↑校验和 = bytes[2..5] 逐字节累加
```

**F1 口（油门信号，发送，12 字节，程序自动发出，不参与判分）**

```
FF 55 | 05 | 08 | float32 小端(输出电压) | 校验和 int16 小端 | FF 55
```
